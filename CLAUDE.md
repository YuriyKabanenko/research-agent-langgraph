# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Self-checking research assistant: takes a topic, drafts a research answer via an LLM (with
web-search and date tools), critiques its own draft, and loops back to research again if the
critique isn't good enough (up to a configurable retry limit). A human then approves or sends
back the result. Three parts:

- **`research_assistant/`**: the LangGraph agent (state machine, prompts, LLM/tool calls).
  Runnable standalone as a CLI.
- **`server/`**: FastAPI app wrapping the agent with bearer-token auth, Postgres persistence
  (SQLAlchemy + Alembic) and an async job API.
- **`frontend/`**: Vite + React + TypeScript SPA (MUI, TanStack Query, Zustand, React Router).

## Environment

- Python venv at `.venv/` (Windows: `.venv/Scripts/python.exe`). `research_assistant` and `server`
  are installed editable from the root `pyproject.toml` and use absolute imports.
- `.env` at the repo root holds API keys, LangSmith and DB settings. Run Python from the repo root.
- Server: `.venv/Scripts/python.exe -m uvicorn server.main:app --reload`
- Migrations: `.venv/Scripts/python.exe -m alembic upgrade head` (review autogenerated revisions:
  they miss renames).
- Frontend: `cd frontend && npm install && npm run dev` (proxies `/api/*` to the server).
- Everything in Docker: `./scripts/up.sh` (services `db`, `migrate`, `back`, `front`).

## Architecture

### `research_assistant/`

`graph.py` builds a `StateGraph` over `ResearchState` (`state.py`):
`validate_input` (invalid → `error_print`) → `assess_topic_complexity`. Simple topics go
`initial_plan` → `research_loop` (subgraph: `llm_research` ↔ `critical_analysis` until the critique
passes or retries run out) → `human_review` (`interrupt()`; approve → `give_final_respond`,
reject → back to `research_loop` with the feedback). Complex topics fan out instead:
`split_topic` → `subtopic_worker` (one per subtopic) → `combine_subtopics`. Node logic lives in
`nodes.py`.

`llm/model.py` wraps Anthropic/OpenAI/Google behind one `ask(...)` call and runs the tool-call loop
itself (tools in `llm/tools.py`). The per-request API key travels via a `ContextVar`, never through
`ResearchState`, so it can't leak into checkpoints or LangSmith traces. The Tavily key works the
same way (`llm/tools.py`), and web search is opt-in per agent (`web_search_enabled`). When the
server has set the Tavily contextvar to `None`, the operator's `TAVILY_API_KEY` env var is never
used, so deployed agents can't spend the operator's credits.

### `server/`

- `main.py`: routes. The graph is compiled once at startup with an `AsyncPostgresSaver`
  checkpointer. `POST /research` creates a `Research` row and runs the graph as a background task
  (`pending` → `running` → `awaiting_review` → `completed`/`failed`). `POST /research/{id}/review`
  resumes it (checkpoint `thread_id` = `Research.id`).
- `db/base.py`: SQLAlchemy models (`User`, `Agent`, `AgentConfig`, `AuthToken`, `Research`).
- `services/`: `AgentService` (start/resume the graph), generic `DBService` CRUD.
- `dependencies.py`: auth and ownership checks (`get_current_user`, `get_agent_service`).

### `frontend/`

`src/api/*.ts` are fetch wrappers per resource. `src/api/types.ts` hand-mirrors the server's
Pydantic models (`server/models/*.py`), so keep them in sync by hand.

## Spec-driven development

If a request includes the flag **"USE SPEC"**, check `specs/` for a matching feature
folder before writing code. If one exists, follow it (`requirements.md` then
`implementation.md`); if not, create it from `specs/_template/` and fill in
`requirements.md` first. See `specs/README.md` for the full workflow.

## Sensitive files

`tokens.txt` at the repo root holds a live API key. Never print its contents, commit it, or copy
it into other files.

## DO NOT

NEVER run agent on your own. All of agent running/testing are done manually.
